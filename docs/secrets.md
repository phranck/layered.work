# Secrets and environment

Every variable the three deployed services read, what it is for, where its value comes from, and what happens without it. No secret value is in this repository. The local values live in the ignored `.env.local`, which starts as a copy of `.env.example`.

## Secrets

Three values on the services are secret. All three are secret variables on the `backend` service, set in the Zerops interface, and nothing else reads them.

| Variable | What it is for | Where it comes from | Without it |
| --- | --- | --- | --- |
| `SESSION_SECRET` | Signs the session cookie. Its strength is its length, so it has at least 32 characters | Generated by `zerops-project-import.yml` as `<@generateRandomString(<64>)>` | In production the backend refuses to start and names the variable. Elsewhere it generates a key per process, so a restart signs everybody out |
| `SMTP2GO_API_KEY` | Sends mail through SMTP2GO | Entered by hand from the SMTP2GO account | Sending is off. The dashboard's SMTP2GO area says the key is missing and refuses a test message |
| `UNSPLASH_ACCESS_KEY` | Searches Unsplash from the media browser and reports each photo taken into the library, as Unsplash's guidelines require | The Access Key of an application registered at unsplash.com/developers, entered by hand | The Unsplash search is off. Searching or taking a photo answers that the key is not set |

The backend's `/health/ready` reports whether each of them arrived, without printing any value:

```bash
curl -s https://backend-2444-3000.prg1.zerops.app/health/ready | jq .configured
```

Both answered `true` on 6 October 2026.

Who mail comes from and the Umami website ID are settings edited in the dashboard rather than variables, because neither is a secret.

Personal access tokens need no secret of their own. Each token carries 256 random bits, and the database keeps only its SHA-256 digest, so a copy of the table gives nobody a usable token.

## What GitHub holds

The deploy workflow reads four repository secrets. Without them nothing deploys.

| Name | What it is |
| --- | --- |
| `ZEROPS_TOKEN` | A Zerops personal access token. Set, and deploying since 13 September 2026 |
| `ZEROPS_BACKEND_SERVICE_ID` | The service id, which `zcli service list` prints and this repository does not |
| `ZEROPS_WEBSITE_SERVICE_ID` | The same, for the website |
| `ZEROPS_DASHBOARD_SERVICE_ID` | The same, for the dashboard |

A service id is a secret because it is the whole address of that service's build trigger, which [Hosting](hosting.md) explains.

The signing key and passphrase for `security.txt` are not set, because that file is not planned for now, which #103 records.

There are no repository variables, as in every sibling project.

## The backend

`apps/backend/src/config.ts` checks the environment once, before the port opens. A value that is required and absent stops the start, and the log names every variable at fault without printing a value.

| Variable | Value in production | Without it |
| --- | --- | --- |
| `NODE_ENV` | `production`, from `zerops.yml` | `development` |
| `HOST` | `0.0.0.0`, from `zerops.yml` | `::` |
| `PORT` | Set by Zerops to the port `zerops.yml` declares | `3000` |
| `LOG_LEVEL` | Not set | `info`, one line per request |
| `DB_MIGRATION_ROLE` | `db`, from `zerops.yml` | The migration runner refuses to run, which stops the deployment before the service starts |
| `SITE_ORIGIN` | `https://layered.work`, from `zerops.yml` | The backend refuses to start |
| `DASHBOARD_ORIGIN` | `https://dashboard.layered.work`, from `zerops.yml` | The backend refuses to start |
| `MEDIA_LOCAL_DIR` | Not set, and ignored in production | Media are read from the bucket |

`SITE_ORIGIN` and `DASHBOARD_ORIGIN` are the two origins that may call the API with a cookie. They come from configuration because a request header is whatever the caller wrote.

## The website

The site reads its variables while it renders, so a missing one shows up on a page rather than at start.

| Variable | Value in production | Without it |
| --- | --- | --- |
| `NODE_ENV` | `production`, from `zerops.yml` | The site's own code does not read it. React and the Astro server inside the build take their development paths |
| `HOST` | `0.0.0.0`, from `zerops.yml` | Every address, from `server.host` in `astro.config.mjs` |
| `PORT` | Not set | `3000`, from `astro.config.mjs`, which is the port `zerops.yml` declares |
| `API_URL` | `http://backend:3000`, from `zerops.yml` | Content comes from the file alone and search runs over that file. A form submission answers that it cannot be sent |
| `WEBSITE_CONTENT_FILE` | The committed snapshot, from `zerops.yml` | Content comes from the backend alone. With neither, every page answers 503 |
| `WEBSITE_MODE` | `auto`, from `zerops.yml` | `auto`, which asks the clock and the host on every request |
| `MEDIA_ORIGIN` | The bucket's CDN address, from `zerops.yml` | A picture's address is its bare storage key, which only the development server answers |
| `MEDIA_LOCAL_DIR` | Not set | No local media are served |

## The dashboard

The dashboard is static files behind nginx, so it reads its two variables while it is built.

| Variable | Value in production | Without it |
| --- | --- | --- |
| `API_ORIGIN` | `http://backend.zerops:3000`, from `zerops.yml` | The same address in a build, and `http://localhost:4002` on the development server |
| `S3_UPLOAD_ORIGIN` | `${assets_apiUrl}`, derived from the bucket | The content security policy leaves the bucket out, so the browser refuses to send an upload there |

## Values derived from another service

Zerops exposes a service's own variables to its siblings, prefixed by the hostname, and `zerops.yml` references them. No value of theirs is written down, and [Hosting](hosting.md) lists the references.

| Variable | Read by | Derived from |
| --- | --- | --- |
| `DATABASE_URL` | backend | `postgres` |
| `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | backend | `assets` |
| `MEDIA_ORIGIN` | website | `assets`, for the bucket name |
| `S3_UPLOAD_ORIGIN` | dashboard | `assets` |

## Reading a secret's length

**A secret's length cannot be read out of `zcli project env`.** That command prints every value wrapped in quotes, and for a secret it prints a fixed-width placeholder rather than the value. Every secret on a service therefore looks the same length:

```text
backend_S3_SECRET_ACCESS_KEY shape: "AAAAAAAA"
backend_SESSION_SECRET       shape: "AAAAAAAA"
backend_SMTP2GO_API_KEY      shape: "AAAAAAAA"
```

That is after replacing every alphanumeric with `A`. `SESSION_SECRET` is over 32 characters, which is why the service starts at all, and it still prints as eight. Ask the application instead, because it reads the real value: a secret that is too short stops the start with `SESSION_SECRET: Too small`.
